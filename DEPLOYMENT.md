# Запуск шаблона у нотариуса

Актуально: 16 сентября 2026. Node.js 24 LTS, Next.js 16, React 19.

## Ветки и демонстрации

| Ветка | Демонстрация | Запись при реальном подключении |
|---|---|---|
| template | https://notarius-wn4h.vercel.app | внешний сервис notariusbot |
| site-lavender | https://notarius-lavender.vercel.app | отдельная PostgreSQL / Prisma |
| site-warm | https://notarius-warm.vercel.app | отдельная PostgreSQL / Prisma |
| site-modern | https://notarius-modern.vercel.app | отдельная PostgreSQL / Prisma |

Для нового проекта клонируйте нужную ветку явно: `git clone --branch template https://github.com/azeall/notarius.git`. Историческая main не является готовой актуальной базой. Дизайн «Дело» — отдельный репозиторий `azeall/notarius-priemnaya`. Витрина и общий сервис — `azeall/notariusbot`.

По умолчанию формы демонстрационные: `NEXT_PUBLIC_BOOKING_MODE=demo`. Они показывают сценарий в браузере и не создают запись. Используйте вымышленные данные. Это не отключает обычные HTTP-запросы сайта и журналирование хостинга.

## Локальная проверка

```sh
npm ci
npm run lint
npm test -- --runInBand
npm run build
npm run typecheck
npm start
```

GitHub Actions выполняет эти проверки при push и pull request. В трёх ветках с Prisma CI дополнительно проверяет миграции и конкурентную запись на отдельной PostgreSQL. Локальные интеграционные тесты разрешены только для специально созданной `127.0.0.1:55432/notarius_booking_test`, с `RUN_BOOKING_PG_TESTS=true` и `BOOKING_TEST_DATABASE_URL`. Никогда не подставляйте рабочую БД.

## Перед включением настоящей записи

1. Заменить демонстрационные ФИО, адрес, телефон, фотографии, документы и отзывы. Сверить услуги, расписание, федеральный и региональный тарифы с нотариусом. Установить `NEXT_PUBLIC_SITE_URL`.
2. Подтвердить фактическое размещение сайта, БД, файлов, журналов и резервных копий. Домен .ru и адрес API не доказывают российское размещение. Проверить внешние шрифты, карты, аналитику, мессенджеры и возможную трансграничную передачу.
3. Утвердить документы с настоящим оператором: нотариусом для его заявок. Штыков Егор Дмитриевич указан в демонстрациях и на витрине как их владелец; его реквизиты нельзя переносить вместо реквизитов нотариуса. Страница `/consent` пока описывает демо и содержит требования к будущему согласию, а не готовое согласие реального нотариуса.
4. Согласовать сроки и процедуры удаления всех категорий данных, включая резервные копии; назначить ответственного за обращения и инциденты. Сроки уведомления РКН 24/72 часа — ч. 3.1 ст. 21 152-ФЗ. Наличие текста на сайте само по себе не организует эту процедуру.
5. Проверить уведомление оператора в РКН, применимость исключений, поручение обработчику по ч. 3 ст. 6 152-ФЗ и условия передачи данных. Политика, согласие и договор решают разные задачи.
6. Настроить секреты, миграции и резервное копирование; проверить восстановление и полный путь заявки на тестовой среде. Только затем включить live, пересобрать сайт и убрать демонстрационные обозначения.

## template: внешний сервис

Установить `NEXT_PUBLIC_BOOKING_MODE=live`, `NEXT_PUBLIC_NOTARYBOT_URL` и `NEXT_PUBLIC_NOTARYBOT_SLUG` конкретного нотариуса. Развернуть проверенную версию notariusbot с миграциями. В его настройках разрешить встраивание только с доменов нотариуса. При недоступном сервисе интерфейс должен сообщать об этом, не выдавая демонстрационный результат за запись.

## Lavender / Warm / Modern: существующая встроенная запись

Эта реализация сохранена для совместимости. Её PostgreSQL независима от общего сервиса notariusbot; переключение на общий сервис потребует явной интеграции, а не замены одного URL.

Необходимы `DATABASE_URL`, `SESSION_SECRET` (32 случайных байта в виде 64 hex-символов), `ADMIN_PASSWORD` и пароли используемых сотрудников `STAFF_1_PASS` … `STAFF_5_PASS` (12–256 символов). Логины задаются `STAFF_n_USER`. Генерация секрета: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Секреты хранить в окружении, не в Git. Смена пароля/секрета прекращает старые сессии; сессии живут 8 часов.

Для пустой базы:

```sh
npx prisma migrate deploy
npx prisma generate
```

Для существующей базы сначала сделать резервную копию и сравнить схему с `20260916000000_baseline`. Только если она соответствует исходной схеме, отметить baseline применённой, затем выполнить новую миграцию:

```sh
npx prisma migrate resolve --applied 20260916000000_baseline
npx prisma migrate deploy
npx prisma generate
```

Миграция сохраняет старые записи; прежним заявкам согласие задним числом не приписывается. Обновить все экземпляры приложения, работающие с этой БД: старые обработчики не используют блокировку конкурентной записи.

`BOOKING_ENABLED=true` разрешает публичную запись на сервере; `NEXT_PUBLIC_BOOKING_MODE=live` включает настоящий интерфейс. До выполнения подготовки оба оставлять выключенными. `TRUST_PROXY_IP=true` разрешён лишь за прокси, который перезаписывает X-Forwarded-For проверенным адресом клиента. Иначе действует консервативный общий лимит. Сервер принимает актуальные `consent: true` и `consentVersion`; после замены текста согласия обновить версию и тесты.

## Поддержка

Исправления общего кода сейчас нужно проверять во всех четырёх ветках. CI каждой ветки — обязательная страховка от расхождения. Объединение дизайнов в одну систему тем — отдельная миграция, а не механическое слияние веток.
